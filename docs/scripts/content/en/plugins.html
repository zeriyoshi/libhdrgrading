Optional processing runs in stages, as filters, and the file formats are read and written by codecs. Filters and codecs are classes of plugins; plugins register through an API table and never link the library. The built-in filters and codecs are plugins of the same ABI, each a CMake project of its own linked into the library and registered when a context is created; a build can leave the optional ones out.

The host side (plugin.h)

  • {{api:hdrg_context_register_plugin}} takes an entry point linked into the app; {{api:hdrg_context_load_plugin}} loads a module from an explicit path (nothing is searched) and checks its ABI version before it can touch the table.
  • The entry point reports the plugin's id, name, version, vendor, SPDX license, copyright, bundled components and status; the host validates every string (length, UTF-8, character set, SPDX syntax, SemVer), applies the app's policy ({{api:hdrg_context_set_plugin_policy}}) and freezes the plugin. A rejected plugin stays listed with its reason ({{api:hdrg_context_plugin_info}}).
  • {{api:hdrg_context_filter_count}}, {{api:hdrg_context_filter_info}} and {{api:hdrg_context_filter_option}} list the filters and their options; {{api:hdrg_options_create}} / {{api:hdrg_options_set}} take options as key=value text; {{api:hdrg_context_add_filter}} adds a filter by id to a stage of the following conversions and sessions (up to six to PREFILTER, one each to INTERP, SCALE, ANALYZE and STATS).
  • {{api:hdrg_context_codec_count}}, {{api:hdrg_context_codec_info}} and {{api:hdrg_context_codec_option}} list the codecs (their extensions, roles, a writer's forms and default form, its options); {{api:hdrg_context_set_writer}} picks the writer of the following still conversions by id, with its options (the default: hdrg.jpeg; a NULL id with options sets the default writer's, NULL with NULL goes back to the defaults). The readers are probed in the order registered.
  • {{api:hdrg_context_set_device}} (in {{src:include/hdrgrading/gpu.h|gpu.h}}) shares the app's GPU device and queue with the filters.

The plugin side (filter.h)

  • A module defines its exports with {{api:HDRG_PLUGIN_DEFINE}}; its entry point receives {{api:hdrg_plugin_api}}, a table of functions grouped by purpose: the plugin's report, memory (the context's allocator), classes, options, the instance's declarations, negotiation, jobs, the ANALYZE and STATS stages' work, reading and writing.
  • Strings cross as (pointer, byte length) and are copied; no enums cross the boundary: constants are uint32_t, the host's objects are opaque handles, and what a stage hands over (side data, the ANALYZE stage's light records, the STATS stage's frames) is plain C structs of the header. Every callback gets the API table as its last argument, so a plugin needs no global state.
  • A class declares its stages and properties ({{api:HDRG_FILTER_PURE}}, {{api:HDRG_FILTER_BANDS}}, {{api:HDRG_FILTER_DETERMINISTIC}}, {{api:HDRG_FILTER_ASYNC}}, {{api:HDRG_FILTER_SEQUENTIAL}}, {{api:HDRG_FILTER_GPU_FRAMES}}: its device jobs take and give the frames shared on the device, {{api:HDRG_FILTER_NO_MOTION}}: an INTERP filter moving nothing, its frames between not capped by the motion), its options with types and ranges, and its callbacks. plugin_set_user and class_set_user set a pointer that every filter and codec of the plugin, or every instance of the class, reads back (filter_plugin_user and filter_class_user; a codec's {{api:hdrg_plugin_api.read_users|read_users}} and {{api:hdrg_plugin_api.write_users|write_users}}), such as a shared device, a model or a GPU class's backend.
  • A codec class ({{src:include/hdrgrading/codec.h|codec.h}}) is a reader or a writer. A reader probes a file's head and decodes it into the picture the host allocates, reporting its color (CICP or ICC), Exif and orientation. A writer declares its forms ({{api:HDRG_OUTPUT_GAINMAP}}, HYBRID, PQ) and default form, its rows (8- or 16-bit R'G'B'), how it signals the color (CICP or ICC) and its largest side; the host gives it the rows band by band and, at the finish, the gain map with its ISO 21496-1 metadata, the alternate rendition's color, an ICC profile, Apple's XMP, the measured light and the Exif, and takes its bytes.
  • An ANALYZE class ({{api:hdrg_plugin_api.class_set_analyze|class_set_analyze}}) has that stage alone, create, destroy and analyze ({{api:hdrg_filter_analyze_fn_t}}), no configure, process or submit, and no flag but DETERMINISTIC. For each frame with judged lights, analyze reads their records with lights_get ({{api:hdrg_light_record_t}}: the box of the light's core in the analyzed frame's pixels, the rules' boost and {{api:HDRG_LIGHT_FEATURES}} features), the analyzed frame as interleaved 16-bit R'G'B' with lights_frame (a session's analysis proxy too; {{api:HDRG_ERR_NOT_FOUND}} where the frame is on the GPU alone), and gives each light its chance with lights_set_chance (one not set keeps 1).
  • A STATS class ({{api:hdrg_plugin_api.class_set_stats|class_set_stats}}) has that stage alone too, create, destroy and six callbacks: window (under a latency profile, the frames before a frame its state reads, which a seek's preroll covers, and the frames after it that must be sent before it renders, which the queue holds), fade (a frame as sent, {{api:hdrg_stats_sent_t}}, into its fade, {{api:hdrg_stats_fade_t}}: the darkening run up to it, whether it holds the statistics the run's first frame rendered with, the dimming its analysis runs again with), frame (its analysis, {{api:hdrg_stats_frame_t}}), render (the frame rendering: stats_head gives the {{api:hdrg_stats_head_t}} whose anchor, key and light boosts it writes, stats_queued the frames queued after it), fit (the APL factor as planned, and one to use instead) and rendered. filter_stats_session describes the session ({{api:hdrg_stats_session_t}}: the mode, the profile, the windows, the first frame, the size, the rate, a TWO_PASS second pass's first pass). The class keeps the session's bytes a pure function of its frames.
  • An instance is created once per conversion or session and configured before each frame. In create it declares its time window (filter_set_window), clip (filter_set_clip), frames in flight (filter_set_max_inflight, required for ASYNC), input format and device; in configure it reads the input's size, color and side data and declares its output size and format, or a passthrough.
  • A job is the rows of a band (BANDS) or a whole frame. process runs it synchronously; an ASYNC filter's submit starts a whole-frame job that ends with job_done from any thread (a driver's completion callback too). A process job takes its scratch memory from job_scratch: the host keeps a block for each worker and grows them all to the most a band's jobs asked for, so the jobs allocate nothing once the frames' sizes are reached.

The ABI stays at {{api:HDRG_PLUGIN_ABI_VERSION}} 1 and is not frozen: until it is, any part may change, and a module built against another version is rejected at load. Build plugins against the library's own header.

The stage runner

{{src:src/host/stage.c}} runs a stage's filter for the pipeline:

  • Band filters get RGB16 rows with the halo they asked for; whole-frame filters get frames in the format they chose (RGB16, RGBA16, planar RGB16 / FP16 / FP32, P016, RGBA8, RGB10A2), converted deterministically from and to RGB16 by {{src:src/host/format.c}}. Whole frames have row pitches of multiples of 256 bytes from a 16 KiB-aligned base, or the filter's own memory (class_set_frames: an IOSurface, pinned CUDA memory).
  • Time windows and clips: a session keeps past + future + in-flight frames in a ring, gives each job its window (and the frames of its shot, job_shot, so a multi-frame model does not mix two shots) and delays the output by the future.
  • ASYNC filters with max_inflight above 1 keep that many jobs in flight under PLAYBACK and OFFLINE; LOW waits for each at once. Frames landed by one stage are handed to the next without a copy when both allocate frames alike.
  • A filter that declared a device kind (filter_set_device) passes its output to a neighboring filter of the same kind on the device (job_device, job_set_output_device).
  • A SCALE filter without BANDS may give a fixed factor (2×, 4×) instead of the size asked for; the runner fits it with its Lanczos.

<gpu> is hdrg.webgpu, hdrg.metal or hdrg.vulkan (for example hdrg.vulkan.deband), built where the build has the backend. A family's GPU classes are in its plugin with its CPU class and declare {{api:HDRG_FILTER_GPU_FRAMES}}, so the library may run a chain of them on its own device frames.

A GPU class asks for the context's device of its kind with {{api:hdrg_plugin_api.filter_gpu_share|filter_gpu_share}}: the native device and queue the host has for the kind (the app's or its own), the lock that submissions to a Vulkan queue take, and for WebGPU a function that runs work on the device's thread (the one thread that uses the device), valid until the plugin's deinit. Only these handles cross from the library to a plugin: the plugin's GPU layer (the hdrgrading-gpu library it links, {{src:src/gpu/include/hdrgrading/gpu|hdrgrading/gpu/}}) wraps them in objects of its own, which in the library's binary are the library's own objects and in a module built apart are the module's on the same device and queue. The frames the GPU filters hand each other on the device are native buffers too (hdrg_gpu_share_frame_t), wrapped by the one that reads them. The share has a version (HDRG_GPU_SHARE_VERSION, {{src:src/foundation/include/hdrgrading/foundation/gpu_share.h|gpu_share.h}}): a plugin built against another gets {{api:HDRG_ERR_UNSUPPORTED}}, as on a context without the device, and its GPU classes do not run.

Plugins as projects

  • Each directory of {{src:src/plugins}} is a CMake project of its own, made with hdrg_plugin ({{src:cmake/HdrgPlugin.cmake}}): its CPU sources, its WebGPU and native GPU (Metal, Vulkan) sources and its WGSL with the generated MSL and SPIR-V beside it. {{src:src/plugins/shared}} holds what several share (the block motion estimation, the denoisers' reading of the noise).
  • The library's build links them in from the start: their objects go into the library, their entry points into a generated registry every context registers in order (the filters, then the codecs). AVIF and HEIF, with dependencies of their own, are always loadable modules.
  • The cache variable HDRG_PLUGINS_EXCLUDE leaves optional ones out ({{dev:build}}): bilinear, denoise, deblock, dering, defringe, deband, mctf, interp, fsr, nis, edge, predict and the codecs jpeg, png, gif, jxl, or the groups filters, codecs and all. Polyphase (the SCALE stage's Lanczos, which also fits a fixed factor) always stays; each codec brings its own dependencies. The library runs without the others: the presets' defaults for a family left out are off (its strength 0, ANIME's and GAME's upscaler Lanczos, PHOTO's video grain PRESERVE without the denoiser), an explicit use is {{api:HDRG_ERR_UNSUPPORTED}}, and a file only a left-out reader takes is {{api:HDRG_ERR_UNSUPPORTED_FORMAT}}. HDRG_WITH_TEMPORAL_INTERP needs interp and HDRG_WITH_TEMPORAL_SR edge; hdrg.stats.temporal comes with HDRG_WITH_TEMPORAL.
  • A project built apart against the installed package (find_package(hdrgrading): hdrgrading::headers, hdrgrading::foundation, hdrgrading::gpu, hdrgrading::plugin_shared) is a loadable module hdrgrading-<name>; {{src:tests/install/run.cmake|test_install}} builds {{src:src/plugins/deband}} so. Ids starting hdrg. are the built-in plugins': a module loaded with one is refused, so a plugin taken out of the library takes an id of its own.
  • The plugins include only the public headers, their own directory and the layers they build on ({{src:src/foundation}}, {{src:src/gpu}}, {{src:src/plugins/shared}}), never the library's internals (scripts/check_style.py checks it).
