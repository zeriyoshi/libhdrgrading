{{api:hdrg_convert}} takes the bytes of an SDR file and returns the bytes of an HDR file; {{api:hdrg_convert_raw}} takes decoded pixels with their H.273 primaries and transfer. Both run the pipeline once and write one of three forms with the context's writer: a codec plugin, JPEG by default, JPEG XL built in, AVIF and HEIF as modules.

{{fig:still}}

The steps

  1. Settings. The three structs are checked and resolved ({{api:hdrg_params_t}}, {{api:hdrg_display_caps_t}}, {{api:hdrg_encode_params_t}}; NULL = the defaults). A still resolves effort AUTO to QUALITY and grain_policy AUTO to PRESERVE (RESYNTH needs the frames of a video and gives {{api:HDRG_ERR_UNSUPPORTED}}). {{api:HDRG_OUTPUT_AUTO|output_mode AUTO}} is the writer's default form.
  2. Format. The context's readers probe the file's head in the order registered (the built-in JPEG, PNG and GIF, then the app's plugins, the AVIF module among them). None that takes it (a PNG or a GIF too, in a build that left that reader out): {{api:HDRG_ERR_UNSUPPORTED_FORMAT}}.
  3. Decode (the reader, {{src:src/host/codec_host.c}}): interleaved R'G'B' of 8 or 16 bits into the picture the host allocates, its color, its EXIF. The size is checked against the context's max_pixels before any pixel is allocated ({{api:HDRG_ERR_LIMIT}}).
  4. Orientation. EXIF orientations 2 to 8 are applied to the pixels, and the EXIF tag carried to the output is set to 1.
  5. Pipeline (see {{page:pipeline}}): opened for the file's assumed viewing, run once, its rows streamed to the writer.
  6. Writer ({{src:src/container.c}}): the rows band by band, then the gain map and its metadata, the profile and the light the form needs; the writer's bytes are the output.

Without lcms2 (HDRG_WITH_LCMS2=OFF) a JPEG's hybrid and PQ forms are {{api:HDRG_ERR_ICC_UNSUPPORTED}} (they need a generated P3 PQ profile), the JPEG writer's target gamut is sRGB, and there is no JPEG XL (libjxl's color management is lcms2's); the writers that signal their color by CICP need no profile. HEIF is written, not read.

The modules are loaded by the app ({{api:hdrg_context_load_plugin}}); hdrg-cli and hdrg-gui load those beside them. Both modules are off by default, and building them is at your own risk ({{dev:build}}). The encoded bytes may depend on the CPU (jpegli and libjxl pick their instructions); the pixels before encoding do not. The AVIF module's bytes are the system's encoder's: libaom's output may change with its version and, in some versions, with the threads it runs on, so the library does not guarantee the same AVIF bytes across runs or machines. It encodes on the conversion's threads by default; threads=1 keeps the bytes of a given libaom the same whatever the conversion's threads (the tests run so).

The assumed viewing

A file has no display to ask, so the container sets one (hdrg_container_caps from the display caps and the encode params): SDR white 203 cd/m², the peak of peak_nits or the format's (1000 cd/m² for PQ; SDR white × 2cap for a gain map, 3 stops by default), Display P3 (for an ICC writer such as JPEG only with lcms2, else sRGB, which needs no profile; the CICP writers' PQ and hybrid bases go in a BT.2020 container). Viewers scale a gain map by their own headroom over the declared one, so a display with less headroom shows every gain scaled down, never below the SDR.

Output size

{{api:hdrg_encode_params_t.output_width|output_width}} and output_height (one side 0 keeps the aspect ratio) run the SCALE stage: a filter added with {{api:hdrg_context_add_filter}}, else the built-in scaler of {{api:hdrg_params_t.upscaler|upscaler}} for an enlargement and Lanczos otherwise. The analysis and the plan stay at the input size.

Results

The output buffer carries its allocator, so {{api:hdrg_free}} works even after the context is destroyed. {{api:hdrg_get_last_stats}} returns what the last successful conversion measured and applied: the diffuse level, the area of lights, the APL before and after, the noise, the blockiness, the ringing and the SIMD tier that ran.
